Unsigned `POST {}` to `/api/internal/safety-status` and `/api/professional/directory/invite/accept-webhook` still return **401** (not 503), i.e. the runtime still has both secrets.

Confirmed two independent ways, both agreeing:
- **`list_secrets` (active run `64eb8c53`, `metadata_available: true`):** `ALIGN_WEBHOOK_SECRET` → `is_empty: false`; `SACOPARENTSALIGN_WEBHOOK_SECRET` → `is_empty: false`. The active run's secret rows **are** the production secrets currently in effect.

  - `not os.environ.get(...)` is true for **absent OR empty**. A 401 is only reachable when the var is **present and non-empty**.
- Both signals → **both keys are present and non-empty in the active production runtime.**
- Caveat: `list_secrets` reads the ACTIVE run only. I cannot read the Secrets-tab/display store independently of the active run. If the user re-deleted the rows AFTER this deploy, the tab may show them gone while the running pod keeps them until the next deploy promotes.

## 3. INTEGRATION_SHARED_SECRET
Present and non-empty (`is_empty: false`). It must stay — status is good, no action needed.

## 4. Re-injection mechanism & how to make removal stick
**Mechanism (per platform secrets model, corroborated by the evidence):** On every redeploy, `write_secrets` composes the pod env by (a) carrying all custom keys **forward from the previous PRODUCTION run's stored env snapshot** (here `b36e37c3`, which held both webhook secrets non-empty), then (b) layering the user's Secrets-tab overrides on top. A tab **EDIT** is recorded as an override and wins. A tab **DELETE** removes the display row but records **no tombstone/override** — so there is nothing to suppress the carried-forward value, and the key is re-injected non-empty. This also matches the user's note that runs `a971d13d` and `5f9b1473` carried these keys prod→prod. The deletion "sticking" in the tab after reload only reflects the display store; the carry-forward source is the previous run snapshot, not that delete.

**This is a documented carry-forward behavior, not a code bug and not this run's `write_secrets` dropping anything.**

**Precise steps that make the removal stick (user action — I cannot edit secrets):**
1. In Deployment Panel → Secrets, do **NOT** delete the rows. Instead **edit** each of `ALIGN_WEBHOOK_SECRET` and `SACOPARENTSALIGN_WEBHOOK_SECRET` and set the value to **empty string**, then Save.
2. Reload to confirm both show as empty/saved.
3. **Redeploy.** `write_secrets` will apply the empty edit as an override that wins over carry-forward.
4. Verify: unsigned `POST {}` to both endpoints should now return **503** (`not os.environ.get(...)` is true for empty), i.e. the webhooks are off — exactly the intended effect. Keep `INTEGRATION_SHARED_SECRET` untouched.

If after an explicit set-to-empty + redeploy the keys still come back non-empty, that would indicate the tab override itself is not being honored by `write_secrets` — a platform-side issue to escalate to Emergent support, quoting deployment `938439ec-1750-4bbb-94ec-0cd7205e17ae` and run `64eb8c53-54b0-4214-baa9-d0893bb3233d`.

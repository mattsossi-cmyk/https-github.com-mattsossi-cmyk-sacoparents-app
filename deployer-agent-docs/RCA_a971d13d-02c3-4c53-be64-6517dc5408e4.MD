# RCA — SACOparents webhook secrets still present after re-deploy

Deployment: prepared-parents (938439ec-1750-4bbb-94ec-0cd7205e17ae)
Live URL: https://sacoparentsapp.online (default: https://prepared-parents.emergent.host)
Re-deploy run investigated: a971d13d-02c3-4c53-be64-6517dc5408e4 (redeploy, success, 02:54:11 → 02:59:58 UTC)

No secret values were printed anywhere in this investigation. All findings use presence/empty/match metadata only.

## Answer to the 4 questions

### 1. Old pods or new rollout?
NEW deployment rolled out. The active run serving traffic is a971d13d, which completed at 02:59:58 UTC and is marked `active_run_id` on the deployment; `deployment_updated_at` = 2026-10-21T02:59:58Z. The brief Cloudflare 520 at 02:59:56 lines up with the promote/traffic-flip + reverse-proxy cache invalidation. The running backend is the NEW image, not old pods.

### 2. Presence in the RUNNING production env (active run a971d13d, via list_secrets)
- ALIGN_WEBHOOK_SECRET → PRESENT, non-empty  ❌ (user expected ABSENT)
- SACOPARENTSALIGN_WEBHOOK_SECRET → PRESENT, non-empty  ❌ (user expected ABSENT)
- INTEGRATION_SHARED_SECRET → PRESENT, non-empty  ✓ (expected present)

This exactly explains the observed live behavior: both webhook endpoints return 401 (bad signature on an unsigned body) rather than 503 (secret missing). The code returns 503 only when the secret is absent from os.environ; it is present, so the "webhook off" path is never taken.

### 3. Public URLs in the RUNNING production env (exact match to https://sacoparentsapp.online)
- PUBLIC_APP_URL → YES (matches_expected = true)
- PUBLIC_BACKEND_URL → YES (matches_expected = true)
- PUBLIC_API_URL → YES (matches_expected = true)
All three are correct.

### 4. Where the webhook secrets come from
They come from the PRODUCTION Secrets store (carried forward from the prior production run) — NOT from the codebase.

Evidence — pulled source for this run (eph sandbox, /app/scratch/backend/.env):
- ALIGN_WEBHOOK_SECRET → NOT in backend/.env
- SACOPARENTSALIGN_WEBHOOK_SECRET → NOT in backend/.env
- INTEGRATION_SHARED_SECRET → present in backend/.env
- PUBLIC_API_URL / PUBLIC_APP_URL / PUBLIC_BACKEND_URL → present in backend/.env but pointing at the PREVIEW URL (https://prepared-parents.preview.emergentagent.com)

Two things follow from this:
- The codebase .env is NOT the source of either webhook secret — it contains neither key. This matches the user's statement (preview .env no longer has SACOPARENTSALIGN_WEBHOOK_SECRET and never had ALIGN_WEBHOOK_SECRET). So preview/codebase .env can be ruled out as the source.
- The PUBLIC_* keys in the codebase .env still point at the preview URL, yet the running prod env has them as the correct sacoparentsapp.online value. That proves the production Secrets store value overrides the preview .env on redeploy — confirming the Secrets store is the authoritative, carried-forward source.

## Root cause
On a redeploy, the custom (user-owned) secrets for the new run are composed by carrying forward the previous production run's stored secrets; the preview/codebase .env only ADDS keys it doesn't already have. ALIGN_WEBHOOK_SECRET and SACOPARENTSALIGN_WEBHOOK_SECRET are still non-empty in the production Secrets store, so they were carried forward into run a971d13d and injected into the running pod. The user's deletion in Manage Publishes → Secrets did not take effect for this run — either it was not persisted/saved before the deploy composed the environment, or it was not registered as an authoritative removal and the carry-forward from the prior production run re-introduced the keys.

## Fix (change nothing was done; this is user action)
In Deployment Panel → Manage Publishes → Secrets, delete ALIGN_WEBHOOK_SECRET and SACOPARENTSALIGN_WEBHOOK_SECRET again, confirm they no longer appear in the list (persisted), then re-deploy. After the redeploy, both endpoints should return 503 ("webhook off") for unsigned requests instead of 401. Keep INTEGRATION_SHARED_SECRET as-is (present). No code change is required — the codebase .env does not contain these keys. PUBLIC_APP_URL / PUBLIC_BACKEND_URL / PUBLIC_API_URL are already correct and need no action.

## Not the cause (ruled out)
- Not old pods: new run is active and live.
- Not the codebase/preview .env: neither webhook key exists there.
- Not a code bug: 401-vs-503 behavior is exactly as designed for present-but-bad-signature.
- Not the PUBLIC_* URLs: all three match the expected value.

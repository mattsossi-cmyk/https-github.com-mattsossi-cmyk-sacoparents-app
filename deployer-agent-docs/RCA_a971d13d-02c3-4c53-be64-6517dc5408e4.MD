# RCA — Webhook secrets still active after re-publish (sacoparentsapp.online)

## Problem statement
After a re-publish the user expected two webhook secrets (`ALIGN_WEBHOOK_SECRET`,
`SACOPARENTSALIGN_WEBHOOK_SECRET`) to be gone, so the webhooks would stop authenticating.
Symptom: unsigned POST `/api/internal/safety-status` returns 401 (not the 503 the code emits
when `ALIGN_WEBHOOK_SECRET` is absent), and `/api/professional/directory/invite/accept-webhook`
returns 401 "Invalid signature." → the running pod still has both secrets set.

## What I verified (tool evidence)

### Current live run (Q4)
`describe_deployment_state`:
- `active_run_id = a971d13d-02c3-4c53-be64-6517dc5408e4`, type **redeploy**, status success.
- created **2026-10-21T02:54:11Z**, completed **2026-10-21T02:59:58Z**.
- `deployment_updated_at = 2026-10-21T02:59:58Z`.
- recent_runs: a971d13d is the newest run. **No deploy run exists after 12:30 UTC 2026-10-21.**
- This is the **same run id** the previous RCA (RCA_a971d13d) diagnosed.

> The build the user believes was published "after ~12:30 UTC 2026-10-21" is NOT represented
> by any new deploy run. The live build is a971d13d from 02:59 UTC. The new JS bundle
> (parallel-builder) shipped inside a971d13d; no later deploy has occurred.

### Secrets on the live run (Q1 + Q3) — `list_secrets` (run a971d13d, metadata_available=true)
- `ALIGN_WEBHOOK_SECRET` → present, **is_empty=false** (set, non-empty).
- `SACOPARENTSALIGN_WEBHOOK_SECRET` → present, **is_empty=false** (set, non-empty).
- `INTEGRATION_SHARED_SECRET` → present, **is_empty=false** (set).
- `PUBLIC_API_URL`, `PUBLIC_APP_URL`, `PUBLIC_BACKEND_URL` → all **matches_expected=true** =
  `https://sacoparentsapp.online`.

### Live behavior
- `preview_health_check` GET `/api/internal/safety-status` → 405 Method Not Allowed (route
  exists, POST-only). Consistent with the user's unsigned-POST 401 evidence. The 401 (not 503)
  proves `ALIGN_WEBHOOK_SECRET` is present in the running pod — matching list_secrets.

## Root cause
The live pod is run **a971d13d**, and both `ALIGN_WEBHOOK_SECRET` and
`SACOPARENTSALIGN_WEBHOOK_SECRET` are present + non-empty in that run's composed environment —
which is why the webhooks still enforce. The intended deletion has NOT taken effect because
**no new deploy run has happened since the run that carries these keys**
(latest run 02:59 UTC; nothing after 12:30 UTC). A pod's environment is frozen at build time;
custom secrets are carried forward from the previous production run on each redeploy. So either:
  (a) the deletion was never saved/persisted in the Secrets tab before a971d13d built, or
  (b) it was done after a971d13d and is still pending — it only applies on the NEXT deploy.
Either way the current live pod still carries both keys.

## Q2 scope note
`list_secrets` reads the **active run (a971d13d) snapshot only**, not the live Secrets-store
state independent of a run. It shows both keys present for the live run. I therefore cannot
confirm from tooling alone whether a post-a971d13d deletion is already staged in the store; I
can only confirm the live run carries them. The fix below handles both cases.

## Fix (user action — platform-side, no code change)
1. Deployment Panel → **Secrets**: delete `ALIGN_WEBHOOK_SECRET` and
   `SACOPARENTSALIGN_WEBHOOK_SECRET`. Keep `INTEGRATION_SHARED_SECRET`.
2. Confirm both rows are gone from the list and the change is saved (re-open the tab to verify
   they do not reappear — if they persist, the earlier deletion did not save).
3. Trigger a **fresh re-publish / redeploy**. This is mandatory: deletion only takes effect on
   the next deploy; the running pod keeps its build-time snapshot until then.
4. After the redeploy completes, verify in Deployment panel that the **active run id changed**
   (no longer a971d13d), then re-test: unsigned POST `/api/internal/safety-status` should return
   **503** (secret absent) instead of 401, and the directory invite webhook should stop
   returning "Invalid signature" for unsigned calls.

Note: custom keys carry forward from the previous production run, so if the deletion is not
actually persisted in the store before the redeploy fires, the new run will re-inherit both
keys again. Persist the deletion first, then redeploy.
